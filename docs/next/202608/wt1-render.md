## 0. 이 지시서의 범위

wt1.md의 2~5단계 — 배치, 렌더, 분위기, 자체 완결 HTML. 1단계(스캔)는 `scan.py`로 끝났다.

만들 것: `render.py`, `template.html`, `vendor/three.bundle.js`.
`scan.py`와 `SPEC.md`는 이 작업에서 고치지 않는다 — 고쳐야 할 일이 생기면 그것 자체가 보고 대상이다.

**1단계에서 얻은 교훈 하나.** 심링크 처리는 스펙 문장으로는 맞았는데 Windows junction에서 실제로
뚫렸다. `is_symlink()`가 False인데 `is_dir(follow_symlinks=False)`는 True였기 때문이다.
**실측하지 않은 동작을 통과로 적지 마라.** 아래 검증 문장은 전부 실제로 돌려서 확인한다.

## 1. 무엇이 어디서 도는가

```
tree.json ──> render.py ──> sprawl.html
              (배치·높이·밝기)   (박스만 세우는 JS + 인라인된 three.js)
```

`render.py`가 좌표까지 계산하고, `template.html`의 JS는 주입된 배열을 받아 렌더만 한다
(SPEC 1-13). 도시가 이상할 때 `tree.json` / `render.py --check` / 브라우저 셋으로 원인이 갈린다.

### 주입 형식

`template.html` 안의 자리표시자를 문자열 치환한다. 배열은 건물 하나당 객체 하나:

```json
{ "x": 12.5, "z": -3.0, "w": 1.4, "d": 1.4, "h": 8.2, "b": 0.73, "n": "scan.py" }
```

`b`는 창문 밝기 0~1, `n`은 파일명(지금은 안 쓰지만 나중에 클릭 인터랙션이 붙을 자리).
구역(폴더) 경계는 바닥 격자를 그리는 데만 쓰므로 별도 배열로 넘긴다.

## 2. 단계별 작업

### A단계 — 배치 (`render.py`)

이 프로젝트에서 유일하게 어려운 부분이다. 먼저 끝내고 나머지로 간다.

- `tree.json`은 **`encoding="utf-8-sig"`로 읽는다.** PowerShell의 `>` 리다이렉트가 BOM을 붙인다.
  이걸 빠뜨리면 `json.load`가 첫 글자에서 죽는다.
- squarified treemap (Bruls et al.). 폴더 구역을 자르고, 그 안에서 재귀적으로 자식 구역을 자른다.
- 구역 면적 가중치는 **자식 파일 개수**다 (SPEC 2-32). 첫 렌더를 보고 재검토한다 — 아래 §3-3.
- 구역 안쪽으로 `STREET` 만큼 여백을 두고, 그 안에 파일 건물을 배치한다 (SPEC 1-10).
- 높이 = `log(size + 1, LOG_BASE) * HEIGHT_SCALE`, 하한 `MIN_HEIGHT` (SPEC 1-12, 2-33).
- 밝기 = `1 - log1p(경과일) / log1p(HALF_LIFE_DAYS)`, 0으로 클램프. 기준점은 **트리 내 최대 mtime**
  이지 스캔 시각이 아니다 (SPEC 1-18). 이걸 틀리면 오래 멈춘 레포가 통째로 캄캄해진다.
- 상수는 파일 상단에 모아 둔다. 눈으로 보고 조정할 값이지 계산으로 맞출 값이 아니다.

`--check`는 렌더 없이 배치만 돌려 겹침·경계를 assert한다 (SPEC 1-14).

> 검증: 이 레포와 `node_modules`가 큰 레포 각각에 `python render.py --check tree.json`이
> 종료 코드 0. 일부러 `STREET`를 음수로 바꾸면 assert가 **실패**하는 것까지 확인한다 —
> 검사기가 실제로 잡는지 보지 않으면 통과는 의미가 없다.

### B단계 — vendor 번들

three.js는 r160부터 UMD를 배포하지 않고, `file://`에서는 `type="module"`의 `import`가 CORS로
막힌다. 그래서 한 번 번들해서 전역 하나로 노출한다 (SPEC 1-22).

필요한 것: `three` 본체, `EffectComposer`, `RenderPass`, `UnrealBloomPass`,
그리고 반사를 쓴다면 `Reflector`.

```
npx esbuild vendor/entry.js --bundle --format=iife --global-name=SPRAWL \
    --minify --outfile=vendor/three.bundle.js
```

빌드는 최초 1회다. 결과물을 레포에 커밋하고, 이후 `render.py`가 그 내용을 읽어 HTML에 박는다.

> 검증: 번들만 넣은 빈 HTML을 `file://`로 열어 `SPRAWL.THREE.REVISION`이 콘솔에 찍힌다.
> 네트워크 탭에 외부 요청이 0건이다.

### C단계 — 렌더 (`template.html`)

- 건물은 `InstancedMesh` 하나. 공유 머티리얼에 per-instance 밝기를 넘긴다 (SPEC 2-43).
  건물마다 머티리얼을 만들면 드로우콜이 파일 수만큼 나온다.
- 창문은 텍스처가 아니라 emissive 격자 (SPEC 1-16). **함정:** 박스 UV를 그대로 쓰면 높은 건물의
  창문이 세로로 늘어난다. 격자 간격을 건물 높이에 비례시켜 창문 크기를 일정하게 만든다.
- 카메라는 `PointerLockControls` + 직접 만든 WASD 이동. addons의 `FlyControls`는 마우스 드래그
  기반이라 "도시 위를 난다"와 다르다.
- **마우스 없이도 조작된다** — 방향키로 시선 회전 (SPEC 2-40). 접근성 기본이라 빼지 않는다.
- 진입 화면에 조작키 안내를 띄우고 `Esc`로 포인터 락에서 빠져나온다 (SPEC 2-40).
- WebGL 초기화를 `try`로 감싸고 실패하면 캔버스 자리에 안내 문구를 남긴다 (SPEC 2-39).

> 검증: 이 레포를 넣고, 방금 고친 파일의 건물이 육안으로 가장 밝다. 1년 전 파일은 어둡다.
> 마우스를 뽑고 키보드만으로 도시를 한 바퀴 돈다.

### D단계 — 분위기

여기서 타협하면 느린 `tree`가 된다 (DIRECTION.md:20-21). 별도 단계로 둔 이유가 그것이다.

- `FogExp2`로 안개, `UnrealBloomPass`로 네온 번짐. 낮 모드도 토글도 없다 (SPEC 1-20).
- 젖은 바닥은 §3-2에서 정한 방식으로.
- 비는 화면 공간에서 싸게 — 파티클 수만 개를 세우지 않는다.

> 검증: 완성 기준 1번. 내 프로젝트를 넣고 스크린샷을 찍어 남한테 보내고 싶은가.
> 아니면 D단계로 돌아간다. 이 판정은 사람이 한다.

### E단계 — 자체 완결

`render.py`가 JSON·번들·JS를 `template.html`에 박아 한 장으로 낸다 (SPEC 1-3).

- 주입 시 `</script`, `<!--`, U+2028, U+2029를 이스케이프한다 (SPEC 2-37). 파일명은 임의 문자열이다.

> 검증: 출력 HTML을 다른 폴더로 옮기고 **랜선을 뽑은 뒤** 더블클릭 → 그대로 뜬다.
> 개발자 도구 네트워크 탭에 요청 0건.

## 3. 지금 결정해야 하는 것

**1. `vendor/entry.js`를 레포에 남기는가.**
남기면 번들을 재현할 수 있지만 SPEC 1-23의 "소스 파일 넷"이 다섯이 된다. 안 남기면 파일 수는
지켜지지만 번들을 다시 만들 방법이 문서에만 남는다.
제안: **남긴다.** 재현 불가능한 800KB 바이너리를 커밋하는 쪽이 더 나쁘다. SPEC 1-23을 갱신한다.

**2. 젖은 바닥을 진짜 반사로 할 것인가.**
`Reflector`는 씬을 한 번 더 그린다 — 건물이 수천 개면 프레임이 반토막 난다. 대안은 낮은
roughness + 블룸으로 젖은 느낌만 내는 것이고, 공짜에 가깝다.
제안: **흉내로 시작.** D단계에서 눈으로 보고 부족하면 그때 `Reflector`를 붙인다.

**3. treemap 가중치 (SPEC S4, `선택 대기`).**
지금 기본값은 파일 **개수**다. 그러면 `node_modules`가 넓이는 지배하되 높이는 지배하지 않아,
DIRECTION.md:57의 "마천루가 스카이라인을 지배" 이미지와 어긋날 수 있다.
첫 렌더 스크린샷을 보고 확정한다 — 그 전에는 바꾸지 않는다.

## 4. 하지 않기로 한 것 (재확인)

구현 중에 가장 손이 가는 순서대로. SPEC 1-25~29에 이미 확정된 것들이다.

1. **LOD·컬링** — 5,000개 넘는 레포에서 느려도 이번엔 손대지 않는다. wt2 몫이다.
2. **건물 클릭** — 레이캐스팅을 붙이고 싶어지는 순간이 온다. `n` 필드는 자리만 잡아둔 것이다.
3. **확장자별 색상** — 전부 같은 네온 팔레트. 도시가 단조로우면 그때 다시 논의한다.
4. **설정 파일·CLI 옵션 확장** — 상수는 소스에 둔다.

## 5. 끝내기 전에

SPEC.md §3 대조를 한다. 1·2절의 각 문장에 대해 그 문장을 참으로 만드는 코드의 파일·줄을 지목한다.
지목하지 못하면 구현되지 않은 것이다. `선택 대기`로 남은 S4·S5·S6·S8·S9·S10·S12는 재확인 목록으로
함께 올린다.
